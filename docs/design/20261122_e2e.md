# Maestro による週次 E2E テスト 設計

- 作成日: 2026-11-22
- ステータス: Draft

## 背景・目的

現在の CI（`.github/workflows/ci.yml`）は、ユニットテスト・Widget テスト（`flutter test`）と静的解析のみを実行している。
ネイティブ連携（Firebase、Google Sign-In、プッシュ通知、地図など）や、実 API（`dotto_app_api`）と組み合わせた画面遷移は自動で検証されておらず、リリース直前の手動確認に頼っている。

[Maestro](https://maestro.dev/) を使って主要ユーザーフローの E2E テストを整備し、**週 1 回スケジュール実行**することで、以下を実現する。

- 依存ライブラリ更新（Renovate）や API 変更による退行を、リリース前に週単位で検知する
- リリース前の手動確認項目を減らす
- 失敗時のスクリーンショット・録画により、原因調査を速くする

## スコープ

### 対象

- アプリ: `apps/dotto`
- Flavor: `stg`（本番相当のバックエンドで、本番データを汚さない）
- プラットフォーム: Android（エミュレータ）を必須、iOS（シミュレータ）を任意で追加
- 主要フロー（後述のテストケース）

### 対象外

- PR ごとの実行（実行時間・コストが大きいため。必要時は `workflow_dispatch` で手動実行する）
- 実機テスト、パフォーマンス計測
- `packages/dotto_design_system` の Widgetbook（VRT は別途検討）

## 方針

| 項目 | 方針 | 理由 |
| --- | --- | --- |
| ツール | Maestro CLI | YAML でフローを書け、Flutter の Semantics を介して要素を特定できる。Android / iOS 共通のフローを書ける |
| 実行頻度 | 週 1 回（月曜 03:00 JST）＋手動実行 | 退行検知には十分で、CI コストを抑えられる。週初めに結果を確認できる |
| ビルド | `stg` flavor の debug なし（profile/release）ビルド | 実運用に近い挙動で検証する |
| 要素特定 | `Semantics(identifier: ...)` を付与し `id:` で指定 | 文言（i18n）変更でテストが壊れないようにする |
| 認証 | ログイン不要フローを優先し、ログイン必須フローはテスト用アカウントで実行 | Google Sign-In の UI 自動化は不安定なため段階導入とする |

## テストケース（初期セット）

| ID | フロー | 内容 | 認証 | タグ |
| --- | --- | --- | --- | --- |
| E2E-01 | 起動 | クリーンインストールから起動し、ホームが表示される。各タブに遷移できる | 不要 | smoke |
| E2E-02 | バス | バス停を選択し、時刻表・便詳細（`bus_trip_screen`）が表示される | 不要 | bus |
| E2E-03 | 学食（Funch） | メニュー一覧が表示され、日付を切り替えられる | 不要 | funch |
| E2E-04 | マップ | マップが表示され、フロア切り替え・検索ができる | 不要 | map |
| E2E-05 | お知らせ | お知らせ一覧から詳細を開ける | 不要 | announcement |
| E2E-06 | 設定 | 設定画面が表示され、バージョン（`app_version_footer`）が表示される | 不要 | setting |
| E2E-07 | 時間割・休講補講 | サインイン後、時間割と休講・補講情報（`course_notice`）が表示される | 必要 | auth |

フロー例（E2E-01）:

```yaml
appId: jp.ac.fun.dotto.stg
tags:
  - smoke
---
- runFlow: ../../subflows/launch_app.yaml
- assertVisible:
    id: root_tab_home
- tapOn:
    id: root_tab_bus
- assertVisible:
    id: bus_screen
- takeScreenshot: smoke_bus
```

`subflows/launch_app.yaml`:

```yaml
appId: jp.ac.fun.dotto.stg
---
- launchApp:
    clearState: true
    permissions:
      notifications: deny
      location: deny
- runFlow:
    when:
      visible:
        id: onboarding_skip
    commands:
      - tapOn:
          id: onboarding_skip
```

> 上記の `id` は導入時に付与する想定の識別子。命名規則は `<画面>_<要素>`（snake_case）とする。

## アプリ側の対応

1. **識別子の付与**: テスト対象の Widget に `Semantics(identifier: 'xxx', child: ...)` を追加する。`RootTabScaffold` のタブ項目（`TabItem`）は識別子を受け取れるようにする。
2. **アニメーション・外部要因の抑制**: 必要に応じて `--dart-define=E2E=true` を追加し、以下を切り替える。
   - 初回オンボーディング・レビュー依頼ダイアログ・強制アップデート（Remote Config）の抑止
   - Firebase Analytics / Crashlytics の送信無効化（計測データを汚さない）
3. **テスト用アカウント**: 大学 Google アカウント相当のテストユーザーを用意し、`stg` 環境のみで有効にする。サインインは Google Sign-In の画面操作ではなく、デバッグ用のトークン注入（`debug` 画面相当の仕組みを `stg` かつ `E2E=true` のときのみ有効化）を検討する。

## CI 設計

新規ワークフロー `.github/workflows/e2e.yml` を追加する。

```yaml
name: E2E

on:
  schedule:
    - cron: 0 18 * * 0   # 毎週月曜 03:00 JST
  workflow_dispatch:
    inputs:
      platform:
        type: choice
        options: [android, ios, all]
        default: android

permissions:
  contents: read
  id-token: write

jobs:
  android:
    runs-on: ubuntu-latest
    timeout-minutes: 90
    steps:
      - uses: actions/checkout@<sha>
      - uses: google-github-actions/auth@<sha>   # ci.yml と同じ WIF 設定
      - uses: ./.github/actions/setup-flutter
      - uses: ./.github/actions/fetch-config
      - name: Enable KVM
        run: |
          echo 'KERNEL=="kvm", GROUP="kvm", MODE="0666", OPTIONS+="static_node=kvm"' \
            | sudo tee /etc/udev/rules.d/99-kvm4all.rules
          sudo udevadm control --reload-rules && sudo udevadm trigger --name-match=kvm
      - name: Build APK
        working-directory: apps/dotto
        run: |
          dart run build_runner build --delete-conflicting-outputs
          flutter build apk --flavor stg --profile \
            --dart-define-from-file=dart_defines/stg.json --dart-define=E2E=true
      - name: Install Maestro
        run: |
          curl -fsSL "https://get.maestro.mobile.dev" | bash
          echo "$HOME/.maestro/bin" >> "$GITHUB_PATH"
      - name: Run E2E
        uses: reactivecircus/android-emulator-runner@<sha>
        with:
          api-level: 35
          arch: x86_64
          profile: pixel_7
          script: |
            adb install apps/dotto/build/app/outputs/flutter-apk/app-stg-profile.apk
            maestro test apps/dotto/.maestro --format junit --output report.xml --test-output-dir maestro-output
      - uses: actions/upload-artifact@<sha>
        if: always()
        with:
          name: e2e-android
          path: |
            report.xml
            maestro-output/
          retention-days: 14
      - name: Notify
        if: failure()
        uses: ./.github/actions/notify-deploy   # 既存の通知アクションを流用 or 汎用化
```

- iOS ジョブは `deploy-app.yml` と同じ `xcode-27` ランナーで、`flutter build ios --simulator --flavor stg` → `xcrun simctl install` → `maestro test` の流れとする。macOS ランナーはコストが高いため、当面は `workflow_dispatch` で `ios` / `all` を選んだときのみ実行する。
- アクションは既存ワークフローと同様にコミット SHA で固定し、Renovate で更新する。
- Maestro のバージョンは `MAESTRO_VERSION` 環境変数で固定する（mise での管理も検討）。

## ローカル実行

`mise.toml` にタスクを追加する。

```toml
[tools]
"ubi:mobile-dev-inc/maestro" = "<version>"   # もしくは公式インストーラ

[tasks."test:e2e"]
dir = "apps/dotto"
run = "maestro test .maestro"
```

手順: エミュレータ / シミュレータを起動 → `flutter run --flavor stg --dart-define-from-file=dart_defines/stg.json --dart-define=E2E=true` でインストール → `mise run test:e2e`。
フローの作成には `maestro studio` を利用する。

## 結果の確認と運用

- 失敗時は通知（Slack 等、既存の通知先）にワークフロー URL を投稿する
- 成果物（JUnit レポート、スクリーンショット、録画）は 14 日保持
- 失敗の一次対応は当番（週替わり）が行い、以下に分類する
  - アプリの退行 → Issue 化して修正
  - テストの不安定（flaky） → `wip` タグで一時除外し、Issue 化
  - 外部要因（stg API 停止など） → 再実行
- flaky 対策として、待機は `extendedWaitUntil` を使い、固定 `sleep` は使わない。ネットワーク待ちは最大 30 秒とする

## 導入ステップ

1. **Phase 1**: Maestro のセットアップ、`launch_app` サブフローと E2E-01（smoke）を作成。`e2e.yml`（Android のみ）を追加し、手動実行で安定性を確認する
2. **Phase 2**: 識別子の付与を進め、E2E-02〜06 を追加。週次スケジュールを有効化する
3. **Phase 3**: テスト用アカウントとサインイン手段を整備し、E2E-07 を追加する
4. **Phase 4**: iOS ジョブを追加し、リリース前（`release.yml` 実行前）の手動実行を運用に組み込む
