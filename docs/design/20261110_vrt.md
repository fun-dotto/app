# Visual Regression Testing (VRT) 導入設計

| 項目 | 内容 |
| ---- | ---- |
| 作成日 | 2026-11-10 |
| ステータス | Draft |
| 対象リポジトリ | `fun-dotto/app`、`fun-dotto/infra` |
| 採用技術 | Widgetbook / Golden Test (`flutter_test`) / reg-suit |

## 1. 背景と目的

Dotto アプリは `packages/dotto_design_system` にデザインシステムを持ち、すでに Widgetbook (`widgetbook` 3.25.0) のユースケースを `@widgetbook.UseCase` で定義している。一方、UI の見た目の変化を検知する仕組みはなく、テーマ・色・テキストスタイルの変更や Flutter / `material_ui` のアップデートによる意図しない見た目の崩れは、レビュアーの目視に頼っている。

本設計では VRT を導入し、次を実現する。

- PR で UI の見た目が変わった箇所を、差分画像付きのレポートとして確認できる。
- 新しい UI コンポーネントを追加するときは Widgetbook にユースケースを追加するだけで、VRT の対象にもなる (二重メンテナンスを避ける)。
- スクリーンショット画像を Git に入れない (リポジトリの肥大化と、画像バイナリのマージコンフリクトを避ける)。

### 非目標

- 実機・シミュレーターを使った E2E の画面キャプチャ (Patrol / integration_test など)。
- iOS / Android のネイティブ描画差の検知。VRT は Linux 上の Flutter テスト描画に統一する。
- 初期段階での PR マージブロック (後述の「段階導入」を参照)。

## 2. 全体像

```text
┌────────────────────────── fun-dotto/app ──────────────────────────┐
│                                                                    │
│  Widgetbook UseCase (@widgetbook.UseCase)  ← 唯一の画面定義        │
│     │                                                              │
│     ├─▶ Widgetbook アプリ (人が見る・触る)                          │
│     │                                                              │
│     └─▶ Golden Test (flutter test --tags vrt)                      │
│            └─ 全 UseCase を PNG に書き出す                          │
│                 build/vrt/actual/**/*.png                          │
│                      │                                             │
│                      ▼                                             │
│               reg-suit compare / publish                           │
│                (GitHub Actions: vrt.yml)                           │
└──────────────────────┬─────────────────────────────────────────────┘
                       │ Workload Identity Federation (キーレス)
                       ▼
┌────────────────────────── fun-dotto/infra ─────────────────────────┐
│  GCS バケット swift2023groupc-app-vrt                                │
│    └─ <commit-sha>/ に actual 画像・差分画像・HTML レポート・out.json│
│  Terraform (Digger) で管理                                           │
└─────────────────────────────────────────────────────────────────────┘
```

役割分担は次のとおり。

| 要素 | 役割 |
| ---- | ---- |
| Widgetbook | 「どの見た目を検証対象にするか」を定義するカタログ。人間が見るためのビューアも兼ねる。 |
| Golden Test | Widgetbook のユースケースを全件レンダリングして PNG に書き出す**キャプチャ係**。画像の合否判定はしない。 |
| reg-suit | ベースライン画像と今回の画像を比較し、差分レポートの生成・保存・通知を行う**比較係**。 |
| GCS | ベースライン画像・レポートの保存先。 |

> **設計判断: Golden Test では合否判定しない。**
> `flutter test` 標準の golden 比較 (`matchesGoldenFile`) は、ベースライン画像を Git に置く前提である。本設計ではベースラインを GCS に置き、比較を reg-suit に任せる。そのため Golden Test 側は専用の `GoldenFileComparator` で「常に成功し、渡されたバイト列を `build/vrt/actual/` に書き出すだけ」にする。これにより、ベースライン管理が 2 系統 (Git と GCS) に分かれることを避ける。

## 3. アプリ側の設計 (`fun-dotto/app`)

### 3.1 ディレクトリ構成

```text
app/
├── .github/workflows/vrt.yml                 # 新規: VRT ワークフロー
├── docs/design/20261110_vrt.md               # 本書
├── mise.toml                                 # タスク追加
├── pubspec.yaml                              # melos スクリプト追加・unit test から vrt タグを除外
├── vrt/
│   ├── package.json                          # reg-suit と plugin をバージョン固定
│   ├── package-lock.json
│   └── regconfig.json                        # reg-suit 設定
└── packages/dotto_design_system/
    ├── dart_test.yaml                        # vrt タグの宣言
    ├── pubspec.yaml                          # dev_dependencies に flutter_test を追加
    └── test/vrt/
        ├── vrt_test.dart                     # 全 UseCase をキャプチャするテスト
        ├── vrt_golden_comparator.dart        # 書き出し専用の GoldenFileComparator
        └── vrt_fonts.dart                    # テスト用フォントのロード
```

`vrt/` は Node の依存 (reg-suit) を Dart のワークスペースから隔離するためのディレクトリである。`vrt/package.json` に reg-suit 本体とプラグインを**完全固定バージョン**で書く。mise の `npm:` バックエンドでグローバルに入れる方式は、reg-suit がプラグインをカレントの `node_modules` から解決するため採用しない。依存更新は Renovate (`renovate.json` が既にある) に任せる。

### 3.2 Widgetbook (既存資産の活用)

`packages/dotto_design_system/lib/main.dart` と `@widgetbook.UseCase` はすでに存在するため、**Widgetbook 自体の新規構築は不要**。VRT のために行う変更は次の 2 点のみ。

1. **決定論的な描画にする**: アニメーションを伴うユースケース (`CircularProgressIndicator` など) は、フレームごとに結果が変わり差分ノイズになる。ユースケース側で固定状態にするか、VRT 対象から除外できるようにする (後述の除外規約)。
2. **ユースケース名を安定させる**: 画像ファイル名はコンポーネント名・ユースケース名から決まるため、ユースケース名の変更は「旧画像の削除 + 新画像の追加」として検出される。リネームは意図的なものに限る。

#### VRT 対象外にする規約

`@widgetbook.UseCase` にはカスタムメタデータを持たせにくいため、ユースケース名の接頭辞で除外を表す。

- 名前が `[no-vrt]` で始まるユースケースはキャプチャしない。

### 3.3 Golden Test (キャプチャ)

#### 方針

`flutter_test` を使い、Widgetbook のコード生成が出力する `directories` (`main.directories.g.dart`) を走査して、全ユースケースを 1 件ずつレンダリング・撮影する。ユースケースを追加すると自動で VRT の対象になる。

```dart
// packages/dotto_design_system/test/vrt/vrt_test.dart (擬似コード)
@Tags(['vrt'])
library;

void main() {
  setUpAll(() async {
    goldenFileComparator = VrtGoldenFileComparator(
      outputDir: Uri.parse('../../build/vrt/actual/'),
    );
    await loadVrtFonts();
  });

  for (final entry in collectUseCases(directories)) {
    // entry.path 例: 'DottoButton/Contained'
    testWidgets(entry.path, (tester) async {
      await tester.binding.setSurfaceSize(const Size(390, 844));
      tester.view.devicePixelRatio = 2;
      addTearDown(() => tester.view.resetDevicePixelRatio());

      await tester.pumpWidget(
        MaterialApp(
          theme: DottoTheme.v2,
          home: Material(
            child: Builder(builder: (context) => entry.useCase.builder(context)),
          ),
        ),
      );
      await tester.pumpAndSettle();

      await expectLater(
        find.byType(MaterialApp),
        matchesGoldenFile('${entry.path}.png'),
      );
    });
  }
}
```

実装時の確認事項:

- `directories` の型 (`WidgetbookNode`) を辿って `WidgetbookUseCase` を取り出す走査関数 `collectUseCases` を自前で書く。Widgetbook 3.x の公開 API で届くことを PoC で確認する。
- `loadVrtFonts` の実装上、Widgetbook アプリ (`main.dart`) と同じテーマ (`DottoTheme.v2`) を使い、見た目が Widgetbook と一致することを保証する。

#### 描画の決定性を確保する

VRT で最も重要なのは「同じコードなら毎回同じ画像になる」ことである。以下を満たす。

| 論点 | 対応 |
| ---- | ---- |
| フォント | `flutter test` 既定の Ahem フォント (四角形) では意味のある差分にならない。アプリが使うフォントファイルをリポジトリ内 (`test/vrt/fonts/`) に置き、`FontLoader` でロードする。使用フォントとライセンスは実装時に確認する (**要確認**)。 |
| OS・レンダラ差 | 画像生成は **CI (`ubuntu-latest`) を正**とする。ローカル (macOS) で生成した画像は比較に使わない。ローカルでは `mise run vrt:capture` で撮影のみ可能だが、差分判定は CI のみ。 |
| Flutter バージョン | `mise.toml` の `flutter = "3.47.8"` に固定済み。Flutter のアップデート PR (Renovate) は描画差分を生みうるが、それ自体が VRT の検出対象であり正しい挙動。 |
| 画面サイズ・DPR | 論理 390×844、DPR 2 に固定。 |
| 時刻・乱数・アニメーション | 固定値を注入する。`pumpAndSettle` が終わらないユースケースは `[no-vrt]` にする。 |
| テキストスケール | 1.0 固定。 |

#### 既存の unit test への影響

`pubspec.yaml` の melos スクリプト `test:unit_tests` は `--dir-exists=test` で `flutter test` を回すため、`packages/dotto_design_system/test/` を作ると**既存の Test ジョブで VRT のキャプチャも走ってしまう**。次のとおり分離する。

- `packages/dotto_design_system/dart_test.yaml` に `tags: { vrt: {} }` を宣言する。
- `test:unit_tests` の `flutter test` に `--exclude-tags vrt` を追加する。
- VRT 用に `melos` スクリプト `test:vrt` (`flutter test --tags vrt --no-pub` を `packageFilters.scope: dotto_design_system` で実行) を追加する。

#### 代替案: `alchemist` / `golden_toolkit`

Golden Test 支援パッケージ (`alchemist` など) は、複数テーマ・複数条件のマトリクス撮影を簡潔に書ける。ただし本設計は「Widgetbook のユースケースを唯一の定義にする」ことを優先し、依存を増やさずに済む自前の薄いコンポーネントで始める。マトリクスが必要になったら再検討する。

### 3.4 reg-suit

#### `vrt/package.json`

```json
{
  "private": true,
  "devDependencies": {
    "reg-suit": "<固定バージョン>",
    "reg-keygen-git-hash-plugin": "<固定バージョン>",
    "reg-publish-gcs-plugin": "<固定バージョン>"
  }
}
```

バージョンは導入時点の最新安定版で固定し、PoC で動作確認してから確定する (本書では未確定)。

#### `vrt/regconfig.json`

```json
{
  "core": {
    "workingDir": ".reg",
    "actualDir": "../build/vrt/actual",
    "thresholdRate": 0,
    "addIgnore": true,
    "ximgdiff": { "invocationType": "client" }
  },
  "plugins": {
    "reg-keygen-git-hash-plugin": true,
    "reg-publish-gcs-plugin": {
      "bucketName": "swift2023groupc-app-vrt"
    }
  }
}
```

- `reg-keygen-git-hash-plugin`: 現在のコミット SHA を「実際 (actual) のキー」、PR のベースブランチ (main) 上で**画像が公開済みの直近の祖先コミット**を「期待 (expected) のキー」とする。VRT をパスフィルタ付きで動かしていても、最後に VRT が走った main のコミットがベースラインになる。
- `reg-publish-gcs-plugin`: 画像・差分・HTML レポートを GCS に保存し、期待値の取得にも使う。認証は Application Default Credentials (`google-github-actions/auth` が設定) を使うため、キーファイルは不要。
- `thresholdRate: 0`: 描画を決定的にしたうえで、まず 1 ピクセルの差も検出する設定で始める。ノイズが多ければ `thresholdPixel` / `matchingThreshold` で調整する。
- GitHub への通知は reg-suit のプラグインではなく、ワークフロー内で `reg-suit` が出力する `.reg/out.json` を読み、`GITHUB_TOKEN` で PR コメントを更新する (後述)。外部の GitHub App 連携を避け、権限を GitHub Actions 内に閉じるため。

### 3.5 mise タスク

`mise.toml` に次を追加する。

```toml
[tasks."vrt:capture"]
description = "Widgetbook の全ユースケースを PNG に書き出す (build/vrt/actual)"
run = [
  { task = "generate:build_runner" },
  "rm -rf build/vrt/actual",
  "melos run test:vrt --no-select",
]

[tasks."vrt:install"]
run = "cd vrt && npm ci"

[tasks."vrt:compare"]
run = "cd vrt && npx reg-suit compare"

[tasks."vrt:publish"]
run = "cd vrt && npx reg-suit publish"
```

`vrt:compare` / `vrt:publish` はベースラインの取得に GCS 認証が必要なため、通常は CI から実行する。

### 3.6 GitHub Actions: `.github/workflows/vrt.yml`

既存の `ci.yml` と同じく、アクションは SHA 固定、`permissions` は最小権限、`concurrency` で重複実行をキャンセルする。

```yaml
name: VRT

on:
  push:
    branches: [main]
    paths:
      - "packages/dotto_design_system/**"
      - "apps/dotto/lib/presentation/**"
      - "vrt/**"
      - "mise.toml"
      - "pubspec.yaml"
      - "pubspec.lock"
      - ".github/workflows/vrt.yml"
  pull_request:
    types: [opened, ready_for_review, reopened, synchronize]
    paths:
      - "packages/dotto_design_system/**"
      - "apps/dotto/lib/presentation/**"
      - "vrt/**"
      - "mise.toml"
      - "pubspec.yaml"
      - "pubspec.lock"
      - ".github/workflows/vrt.yml"
  workflow_dispatch:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read
  id-token: write
  pull-requests: write # PR コメントの更新

jobs:
  vrt:
    name: VRT
    if: >-
      github.event_name != 'pull_request' ||
      (github.event.pull_request.draft == false &&
       github.event.pull_request.head.repo.full_name == github.repository)
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@<SHA> # ci.yml と同じ固定 SHA
        with:
          fetch-depth: 0 # git-hash plugin が祖先コミットをたどるため全履歴が必要
      - uses: google-github-actions/auth@<SHA>
        with:
          project_id: swift2023groupc
          workload_identity_provider: ${{ vars.GCP_WORKLOAD_IDENTITY_PROVIDER }}
          service_account: ${{ vars.GCP_SERVICE_ACCOUNT }}
      - uses: ./.github/actions/setup-ci
      - run: mise run vrt:install
      - run: mise run vrt:capture
      - run: mise run vrt:compare
      - run: mise run vrt:publish
      - name: Comment on PR
        if: github.event_name == 'pull_request'
        uses: actions/github-script@<SHA>
        with:
          script: |
            // vrt/.reg/out.json を読み、changed / new / deleted の件数と
            // レポート URL を <!-- vrt-report --> マーカー付きコメントとして作成または更新する
```

ポイント:

- **`push: main` でもベースラインを発行する**: main にマージされた時点の画像が次の PR のベースラインになる。PR をマージすること自体が「差分の承認」であり、別途の承認操作は設けない。
- **fork からの PR はスキップする**: fork の PR には `id-token` が発行されず GCP へ認証できない。このリポジトリは public のため、`head.repo.full_name == github.repository` を条件にする。
- **Draft PR はスキップする**: `ci.yml` と同じ方針。
- **パスフィルタ**: UI に関係しない変更で VRT を走らせない。`pubspec.lock` / `mise.toml` / ワークフロー自体を含めるのは、依存や Flutter のバージョン変更が描画に影響しうるため。PR のパスフィルタで VRT が走らなかったコミットは、reg-suit が祖先をたどって直近のベースラインを使うため問題ない。
- **ジョブは差分があっても成功させる**: reg-suit は差分があっても終了コード 0 で終わる。差分は PR コメントとレポートで人が判断する (段階導入を参照)。
- PR コメントは、同一 PR で 1 件を更新し続ける (コメントの乱立を防ぐ)。コメント投稿は GitHub に外部公開される動作なので、ワークフローが投稿するのは本文にレポート URL と件数のみとする。

### 3.7 段階導入

| フェーズ | 内容 | マージブロック |
| -------- | ---- | -------------- |
| 1 | デザインシステム (`dotto_design_system`) の Widgetbook ユースケースを対象にする。ここまでを本設計のスコープとする。 | しない (情報提供のみ) |
| 2 | 画面単位の VRT。`apps/dotto/test/presentation` に Riverpod の override と既存の `test/helpers/fake_*` を使った画面の撮影テストを追加し、同じ `build/vrt/actual` に出力する。 | しない |
| 3 | 誤検知率が十分低いことを確認できたら、`VRT` を必須ステータスチェックにするか検討する。 | 要判断 |

`VRT` を必須にする場合は infra リポジトリの `terraform/github/fun-dotto/repository-app.tf` の `required_status_checks = ["Test", "Lint"]` に `"VRT"` を追加する。ただしパスフィルタ付きワークフローは、条件に合わない PR ではジョブ自体が走らず**必須チェックが永遠に pending になる**。必須化するときは、パスフィルタを外すか、常に走る軽量なゲートジョブを用意する。

## 4. インフラの設計 (`fun-dotto/infra`)

既存の構成 (GCP プロジェクト `swift2023groupc`、リージョン `asia-northeast1`、Terraform + Digger、GitHub Actions は Workload Identity Federation でキーレス認証) に沿って、**新しい種類のリソースは GCS バケット 1 つとその IAM のみ**にとどめる。新しい認証基盤やサービスは増やさない。

### 4.1 変更一覧

| 対象 | 変更 |
| ---- | ---- |
| `terraform/google/foundation/cloud-storage/vrt.tf` (新規) | VRT 用バケットと IAM |
| `terraform/google/foundation/cloud-storage/variables.tf` (新規または既存追記) | レポート閲覧者のリスト |
| `digger.yml` | 変更不要 (`foundation-cloud-storage` project が既にある) |
| `terraform/github/fun-dotto/repository-app.tf` | フェーズ 1 では変更なし (必須チェックに加えない) |

### 4.2 GCS バケット

```hcl
# terraform/google/foundation/cloud-storage/vrt.tf
resource "google_storage_bucket" "app_vrt" {
  name     = "swift2023groupc-app-vrt"
  location = var.google_cloud_region

  uniform_bucket_level_access = true
  public_access_prevention    = "enforced"

  # 古いベースライン・PR のレポートを自動で削除する
  lifecycle_rule {
    condition {
      age = 90
    }
    action {
      type = "Delete"
    }
  }
}
```

設計の根拠:

- **非公開 (`public_access_prevention = "enforced"`)**: 現状はデザインシステムのコンポーネント画像のみだが、フェーズ 2 で画面を撮影すると内部情報が写る可能性がある。リポジトリが public であっても、レポートは非公開にする。
- **保持期間 90 日**: reg-suit は PR のベースライン探索で過去コミットの画像を参照するだけなので、長期保存は不要。90 日を超えて更新されていないブランチと比較する場合は「ベースラインなし (すべて New 扱い)」になるが、実害はない。
- **バージョニング・ソフト削除は設けない**: 画像は再生成可能であるため。
- `lifecycle { prevent_destroy }` は付けない (再生成可能なデータのため)。tfstate バケット (`tfstate.tf`) とは異なる扱いとする。

### 4.3 IAM

#### 書き込み権限 (GitHub Actions)

既存の `github-actions-app` サービスアカウント (`service_account_github-actions-app.tf`) を再利用し、**プロジェクト全体ではなくバケット単位**で権限を付ける。

```hcl
data "google_service_account" "github_actions_app" {
  account_id = "github-actions-app"
}

resource "google_storage_bucket_iam_member" "app_vrt_github_actions" {
  bucket = google_storage_bucket.app_vrt.name
  role   = "roles/storage.objectUser"
  member = "serviceAccount:${data.google_service_account.github_actions_app.email}"
}
```

- `roles/storage.objectUser` は、オブジェクトの作成・取得・一覧・更新・削除ができ、バケット自体や ACL の変更はできない。reg-suit の公開・期待値取得に必要十分である。
- バケット IAM を `iam-workload-identity` のプロジェクトではなく `cloud-storage` のプロジェクトに置くのは、**Terraform の remote state 参照を増やさない**という既存方針に合わせるためである (既存のコードも、依存先を `data` や組み立てた名前で参照している)。このため、`iam-workload-identity` が `github-actions-app` を作成済みであることが前提となる (既に作成済み)。

#### 信頼境界についての注意

Workload Identity のプリンシパルは `principal://.../subject/fun-dotto/app` (リポジトリ単位) で、ブランチやワークフローでは区別されない。つまり `fun-dotto/app` の**どの PR ワークフローからでも**このバケットへ書き込める。想定される影響と緩和策:

- PR 上のコードが main のベースラインを汚染する可能性: reg-suit のキーは**コミット SHA**であり、PR のコミットは main の履歴に存在しないため、PR のワークフローが main のキー配下を書き換える動機・経路は通常の運用では生じない。ただし権限上は書き込めてしまうため、悪意のあるコードを含む PR を同一リポジトリのブランチから出せる人 (= リポジトリへの書き込み権限者) は信頼する前提とする。
- fork からの PR は `id-token` が得られないため書き込めない。

この前提が許容できない場合は、`google.subject` のマッピングに `ref` や `workflow` を含める (Workload Identity Provider の変更) 必要があるが、他の全ワークフローに影響するため本設計のスコープ外とする。

#### 閲覧権限 (人)

```hcl
variable "app_vrt_viewers" {
  description = "VRT レポートを閲覧できる Google アカウントまたはグループ (例: group:dev@example.com)"
  type        = list(string)
  default     = []
}

resource "google_storage_bucket_iam_member" "app_vrt_viewers" {
  for_each = toset(var.app_vrt_viewers)

  bucket = google_storage_bucket.app_vrt.name
  role   = "roles/storage.objectViewer"
  member = each.value

```

### 4.4 レポートの閲覧方法

`reg-publish-gcs-plugin` は HTML レポートと画像を GCS に置く。バケットは非公開のため、レポート URL (`https://storage.cloud.google.com/swift2023groupc-app-vrt/<commit-sha>/index.html`) を開くには、Google アカウントでログインしたうえで `app_vrt_viewers` に含まれている必要がある。

| 案 | 内容 | 評価 |
| -- | ---- | ---- |
| **A (採用)** | 上記のとおり、Google アカウントの IAM で閲覧を制限する。 | 追加リソースなし。開発メンバーが少人数なら十分。 |
| B | Cloudflare Workers / Pages でレポートを配信し、Cloudflare Access (`GitHub Members` ポリシー) で保護する。既存の Storybook や Server Docs と同じ運用に揃えられる。 | GitHub の組織メンバー管理に一本化できるが、GCS からの配信プロキシと Access アプリケーションの追加が必要。メンバー増加や非 Google アカウントの閲覧者が出てきたら移行する。 |

案 A で `storage.cloud.google.com` 経由の相対リンク (レポートから画像への参照) が正しく開けることは、PoC で確認する (**要確認**)。開けない場合は案 B に切り替える。

### 4.5 適用手順

1. infra リポジトリに PR を出し、Digger の `digger plan` で `foundation-cloud-storage` の差分を確認する。
2. レビュー後 `digger apply` でバケットと IAM を作成する (`terraform-ci` の `roles/storage.admin` で作成可能。バケット IAM の変更に必要な権限も `storage.admin` に含まれる)。
3. app リポジトリの VRT PR をマージする。
   - バケットが存在しない状態でワークフローを走らせると失敗するため、**infra の apply を先に行う**。

## 5. 運用

### 5.1 開発者のワークフロー

1. UI を変更する、またはコンポーネントを追加し、Widgetbook のユースケースを追加・更新する。
2. PR を作成する (Draft を外す)。
3. `VRT` ジョブの PR コメントで、`Changed / New / Deleted` の件数とレポートリンクを確認する。
4. レポートで差分を確認し、意図した変更であればそのままレビュー・マージする。意図しない差分があれば修正する。
5. main にマージされると、その時点の画像が新しいベースラインになる。

### 5.2 ローカルでの確認

```bash
mise run vrt:capture
```

`build/vrt/actual/` に PNG が出力される。ただし OS 差があるため、**差分判定は CI のみ**とする。ローカルは「撮影が成功する」「ユースケースが描画できる」ことの確認に使う。

### 5.3 想定されるトラブル

| 症状 | 原因 | 対応 |
| ---- | ---- | ---- |
| 変更していないコンポーネントに差分が出る | アニメーション・時刻・乱数などの非決定要素 | ユースケースを固定状態にするか `[no-vrt]` を付ける |
| すべての画像が差分になる | Flutter / フォント / `material_ui` の更新、または CI ランナーの変更 | 意図した更新か確認し、そのままマージしてベースラインを更新する |
| すべての画像が `New` になる | ベースラインが見つからない (初回、または 90 日超) | 初回は正常。main へのマージ後に解消される |
| ワークフローが GCS 認証で失敗する | infra の apply 未実施、または fork からの PR | apply を確認する。fork の PR はスキップされるのが正しい挙動 |
| 同じ PR で push を繰り返すとレポートが増える | コミットごとに SHA 配下へ保存される | 90 日のライフサイクルで自動削除される |

### 5.4 コスト

- **GCS**: 画像は 1 枚あたり数十 KB、ユースケース数百件で 1 コミットあたり数十 MB 未満。90 日保持でも月額は数円〜数十円規模と見込む (実測して確認する)。
- **GitHub Actions**: パスフィルタにより UI 変更時のみ実行。`ubuntu-latest` で 1 回 5〜10 分程度の想定 (実測して確認する)。

## 7. 未決定事項・要確認事項

1. **閲覧者の管理方法**: `app_vrt_viewers` に入れる Google グループまたはアカウントを決める (開発メンバーが Google アカウントを持っているか)。
